# DNPR panic renderer demo

`dnpr-test` defaults to a parallel simulation of the panic renderer. It loads the same compressed scene, mesh, and highlight lookup as the kernel and compiles the kernel's raster, sprite, region, compose, and blit routines into the demo. Persistent worker threads and the calling thread claim the same 32-row raster bands as the kernel SMP path. It writes two simulated block-linear scanouts to mapped DRM dumb buffers when available, or RAM buffers otherwise. SDL presents a separate copy. `--legacy-preview` selects the older floating-point renderer. Neither mapped dumb buffers nor SDL presentation are the actual panic scanout, so a demo benchmark cannot establish the physical panic's exact FPS.

`--benchmark-panic` measures unthrottled render throughput, not monitor refresh or live playback rate. It accepts optional `--from N`, `--to N`, and `--total-frames N`; defaults are frames 0 through 6 (seven frames). Frame numbers sample the 30 Hz animation clock. A specified starting frame gets one untimed predecessor to establish incremental-render state. The output separates animated and settled averages, plus preparation, 3D rasterization, composition, scanout blit, and preview-copy costs. A combined average across both phases is not the animation FPS. `--panic-threads N` selects 1–16 raster threads; the default uses online CPUs, capped at 16. Use `--panic-threads 1` for the old serial baseline and `--no-drm-buffer` to benchmark RAM scanouts. `--unshaded` keeps geometry and depth testing but draws flat triangle colours; `--no-specular` keeps diffuse shading but omits highlights. These are mutually exclusive simulator diagnostics and never change the kernel panic image. The live demo follows the kernel's 144 Hz maximum throughout, including after the head settles; actual draws may take longer. Star and sparkle textures still advance on their independent 12 fps animation clock. A 60 Hz display can still show repeated content frames.

The original floating-point renderer described below runs only with `--legacy-preview`.

The legacy preview does not trigger a kernel panic. It renders the user-provided SuperGodot64 head geometry and game-over animation with a software depth buffer, Gouraud lighting, a tiled background, two spinning star sprites (one silver, one red), animated gold sparkles around the silver star, small animated red sparkles around the red star, and a flickering reboot prompt at the lower left. The prompt stacks `REBOOT`, `YOUR`, and `DEVICE` beside Mario, with the silver star underneath, following the supplied placement reference. It uses the SuperGodot64 colorful title glyph textures, sharing the V tile for U. Displays at 720p and above use a 128×128 atlas baked from the HD source; lower resolutions use a 16×16 atlas. Diffuse colour remains bright; interpolated normals add a separate reflective highlight. `export_head.py` bakes 131 posed frames from the local JSON into `mario_head.bin`. Playback drives the head from elapsed time like the kernel does: while the animation runs, each vsync tick blends the vertex positions between the adjacent baked poses around the current pose clock and recomputes the smooth normals from the blended surface, so a fast panel can see interpolated poses; when rendering falls behind, the pose clock skips source poses the same way the panic draw does. The star, sparkle, and prompt overlays keep their own clocks. Playback freezes on the half-lidded sigh pose at zero-based frame 130; stars and particles keep moving. `export_scene.py` bakes the four original game-over background strips, 16 star frames, both prompt atlases, and six sparkle frames. `export_audio.py` captures the local ROM's game-over phrase and Mario's voice through the same endpoint. The audio continues after the pose freezes and ends at the near-silent break just before the title phrase. These game-derived assets should remain local unless their distribution rights are established.

## Build and run

```sh
make
./dnpr-test --displays
./dnpr-test
./dnpr-test --no-audio
./dnpr-test --frame-step
./dnpr-test --static
./dnpr-test --animation
./dnpr-test --status
./dnpr-test --stop
./dnpr-test --benchmark-panic --from 40 --to 46
```

The build needs Python 3 with NumPy and Pillow, SDL2 development files, the SuperGodot64 head and texture files, its local ROM, and its local `libsm64.so` mixer. Set `SUPERGODOT64_ROOT=/path/to/SuperGodot64` when the reference project is elsewhere. The generated game assets and preview binaries are intentionally excluded from this repository.

Audio is on by default; `--no-audio` disables it. `--frame-step` opens on frame 0 and pauses there. Press F to advance one 30 FPS animation frame and play that frame's audio slice; the selected frame is printed in the terminal. This is useful for capturing the first few poses. Escape exits. `--render-frame preview.ppm` writes a headless 1920×1080 still image of the full scene; `--render-base-frame base.ppm` writes the same pose without the star, sparkle, and prompt overlays, which is the base the kernel panic asset bakes; `--frame N` samples the panic renderer at that frame's integer-millisecond timestamp; `--time-ms N` selects an exact millisecond timestamp. The fullscreen demo presents at the selected display's native mode. `--display N` can select any SDL display. Without an explicit selection, the preview prefers an identified Acer and otherwise uses display 0. The current machine's Acer X233H is DVI-D-1, SDL display 0; the Microstep MP242 is HDMI-A-1, SDL display 1.

The background keeps its stretched 16:9 tile geometry and repeats additional tiles on wider screens. Sparkles use 128×128 HD frames at 720p and above and 32×32 SD frames below 720p.

The legacy preview uses SDL's compositor-managed fullscreen desktop window. Hyprland retains DRM master and the display mode. The legacy preview rasterizes into a RAM image, bulk-copies that image to a CPU-mappable DRM dumb buffer, and presents the RAM image through an SDL window surface on the Acer. It does not create an SDL renderer or streaming texture. Direct rasterization into the mapped NVIDIA buffer followed by SDL readback was measured at roughly 0.01 fps; the panic path never reads scanout back. If a mapped DRM buffer is unavailable, it logs the fallback and presents the RAM image. `--no-drm-buffer` disables the extra DRM copy for a baseline. The dumb buffer is linear and is not the proprietary driver's block-linear panic scanout, so preview FPS is not a kernel panic FPS measurement. Closing the window restores the prior desktop state without changing connector routing. The control socket lives at `$XDG_RUNTIME_DIR/dnpr-test-UID.sock`; a stale socket is replaced only after a failed connection. A process crash closes its Wayland window, so it cannot retain display ownership. Both preview renderers use persistent worker threads created once at startup; each frame the workers and the calling thread grab 32-row bands from an atomic queue, so rows never straddle threads and the depth buffer needs no locking.

## Verified on this system

- The shared panic core compiled as a userspace simulator and as a kernel object. Seven sampled frames at 0, 100, 500, 1000, 2000, 3000, and 4333 ms remained byte-identical after front-to-back triangle ordering with original-index depth ties. On the current RAM fallback, rasterization at animation frames 40–46 fell from roughly 18.7 ms to 16.5 ms per frame; this is not a measured physical-panic speedup.
- A seven-frame growth benchmark (frames 19–25) improved from 35.3 ms to 30.9 ms average in the RAM simulator after nearest-depth ordering, fully hidden scanline rejection, and conservative zero-highlight elimination. Frame 22 still takes about 43 ms, so a stable 30 FPS through the growth peak is not yet established. Back-face culling changed visible pixels and was discarded; the rebuilt demo matches saved growth-frame images byte-for-byte.

- Kernel: Linux 6.15.2, `CONFIG_DRM_PANIC=y`.
- GPU: GTX 1060 bound to proprietary `nvidia` 575.57.08 modules.
- Desktop: Hyprland on Wayland. Acer X233H: 1920×1080 at 60 Hz, DVI-D-1. Microstep MP242: 1920×1080 at 144 Hz, HDMI-A-1.
- SDL enumerated and identified both displays. Hyprland reported the DNPR fullscreen window on monitor 0 (Acer), workspace 2.
- Static preview, animation, audio, status, and stop completed. PipeWire showed a 32 kHz stereo playback stream. A comparison against music-only capture confirmed Mario's voice signal from about 0.5 to 1.5 seconds. The audio ends at 6 seconds with a quarter-second fade over the natural break. The rebuilt audio preview ran on Acer monitor 0 and stopped cleanly. After exit, no DNPR window remained, and both displays retained their modes and workspaces.
- Native-resolution frame generation and build completed without warnings.
- At 1920×1080, a local render benchmark measured about 23.5 ms per changing head pose on one thread. The rasterizer now splits the frame into 32-row bands pulled from an atomic queue by persistent worker threads plus the calling thread, one worker per logical CPU up to 15. On this machine (6 cores, Hyper-Threading, 12 hardware threads) that measures about 5.0 ms per changing pose, a 4.7× speedup, and the 1.1 ms frozen-frame path after caching the completed head image is unchanged. Renders at poses 0, 60, and 130 are bit-identical to the single-threaded build because each row is rasterized exactly once with the same math. A separate 640×360 render verified the low-resolution atlas path.
- Interpolated playback was verified headless: a frac=0 blend reproduces the baked pose bit-for-bit, a frac=0.5 blend lands on the vertex midpoints with unit-length recomputed normals, renders of poses 60, 60.5, and 61 are three distinct images, and the frozen hold after the animation is stable across ticks. The `--frame N` inspection path still renders the exact baked pose.
- Kernel #44: a real panic displayed the shared animated scene on both scanouts and played Mario's game-over cue through the Microstep HDMI, bypassing PipeWire. The audio fix was the raw-deflate blob change; the panic path itself needed no change.
- The preview reads 644 posed 3D vertices and rasterizes 1,213 triangles per frame, with a depth buffer and live SDL audio. Headless renders of poses 0 and 60 have different hashes. This verifies the preview path; it does not verify a kernel panic.

## Kernel panic backend

### Experimental panic-time SMP

The kernel source tree at `/mnt/nvme/dnpr-linux-6.15.2` now arms DNPR before the normal x86 panic CPU shutdown. With `drm.smp=1` on the kernel command line, the existing reboot-vector stop IPI interrupts other CPUs. Responsive CPUs stop their previous work and enter DNPR's 32-row raster queue without being marked offline. A CPU that misses that IPI takes Linux's normal NMI stop path; the responsive CPUs and panic CPU still draw bands. If a helper stalls during a frame, DNPR requests the normal CPU stop and redraws that frame on the panic CPU. The handoff is disabled by default; `drm.smp=0` retains the previous path. It is also bypassed when post-notifier kdump or all-CPU panic backtraces are requested.

The integration change to `kernel/panic.c`, `arch/x86/kernel/smp.c`, and `drm_panic.c` is in `kernel/dnpr-smp-handoff.patch`; apply it after `kernel/dnpr-linux-6.15.2.patch` when preparing a fresh tree. Copy the current `kernel/dnpr_panic.c`, `kernel/dnpr_panic.h`, and shared `kernel/dnpr_*_core.h` / `kernel/dnpr_raster_rows.h` into `drivers/gpu/drm/` before building. The source tree builds `vmlinux` and `arch/x86/boot/bzImage`, but this SMP path has not yet been exercised by a real panic or measured on the scanout. Keep the existing kernel image as a boot fallback when testing it.

Panic HDA audio is disabled by default after reports of loud crackling during panic playback. Re-enable it only for a controlled test with `dnpr_panic.audio=1`; shading helpers remain separate from the audio polling CPU, but that is not a guarantee against controller or codec faults.

The panic base frame is generated from the tiled background strips only. It must not include a frozen Mario head: the live mesh starts at a small pose and grows during panic animation, so a baked final-pose head behind it looks like a second face.

`kernel/dnpr-linux-6.15.2.patch` adds a `CONFIG_DRM_DNPR` panic screen to Linux 6.15.2. A phone video of kernel build #35 showed Mario animate, but the scene restarted on the second monitor because each DRM plane ran its own sequence. Build #41 collects both scanouts before starting one shared animation clock. Both connected outputs report 1920×1080; a preallocated 1080p frame is composed once, then copied to each scanout. Other output sizes use the direct compositor. Mario's 131 posed vertex frames play once and then hold the final sigh. The panic draw has a 144 Hz ceiling and uses elapsed time: when rendering is below 30 fps it skips source poses, and above 30 fps it interpolates between adjacent poses. The 3D scene is rasterized in software into the shared frame. After Mario reaches the final sigh, draws retain the 144 Hz ceiling while star and particle textures keep their independent 12 fps animation clock. Star and particle textures advance on that clock; `REBOOT YOUR DEVICE` changes visibility every 15 original game frames (500 ms). During Mario's animation, the renderer updates the old and new head bounds plus the star and prompt regions. After the head settles, it updates only the star and prompt regions. The small magenta frame counter remains visible as requested; the preview draws the same counter in its live window. The audio source prepares the six-second cue as HDA DMA buffers at boot, then takes over one NVIDIA HDA output stream and routes it to the connected Microstep HDMI codec when the panic starts. It is enabled by default and bypasses PipeWire and sleeping ALSA calls in the panic path. Build #42 reduced per-pixel shading math but changed the visible gloss. Build #43 restores the original shading calculation, scans only conservative triangle spans instead of their full bounding boxes, and skips unchanged pixels in block-linear scanouts. Emit raw deflate from the export script instead, matching the helper's contract, and add stage-wise failure logging to `dnpr_hda_init`. Build #44 fixes the panic audio: `export_panic_audio.py` embedded a zlib-wrapped stream, but the kernel's `zlib_inflate_blob` helper expects raw deflate, so the boot-time decode failed, the module logged `panic HDA PCM unavailable`, and the panic draw ran with no audio at all. After installing #44, a real panic on this machine displayed the animated scene and played the six-second cue through the connected Microstep HDMI as intended. Build #45 added a 32-row SMP queue and a boot-time CRC selftest. That selftest runs while other CPUs are online and confirmed the band renderer, but the normal panic path stops other CPUs before DRM invokes DNPR. The panic-time helper IPIs therefore cannot run. On this x86 kernel, stopped CPUs are also removed from the online mask, so helper startup returned without dispatching work; it did not add a 25 ms wait. Build #47 removes that dead call but is not expected to change FPS. The SMP selftest remains available at boot. Build #48 replaces the seven signed 64-bit divisions per visible head pixel with exact invariant-divisor quotients: one reciprocal is prepared per triangle, then a high-half multiply and one correction reproduce truncating division. The depth, diffuse colours, normals, and gloss formula retain their exact integer results. A focused 8.5-million-quotient benchmark took 43.4 ms with division and 8.6 ms with the exact reciprocal method on this machine. Panic FPS for #48 still needs a quantified recording. The next source change preloads a 16 MiB exact lookup for the integer gloss function from a 96 KiB deflate blob; it removes the per-pixel square root and normal-length division while matching the corrected signed gloss formula for all 8-bit normal triples. The old unsigned length divisor accidentally made negative light dots produce a bright highlight; the fallback now uses signed division too. If that allocation fails, the corrected arithmetic runs. A standalone 3-million-sample gloss benchmark took 33.75 ms arithmetically and 9.35 ms through the lookup. These are component timings, not a measured panic FPS increase. This is kernel build #49, installed at `/boot/vmlinuz-6.15.2-dnpr` with a matching System.map; the running kernel remains #48 until reboot. The previous image is backed up at `/mnt/nvme/vmlinuz-6.15.2-dnpr.pre-spec-lut`. HDA DMA plays audio independently; the panic CPU checks its stop point. Build #46 attempts to stop the panic audio cleanly: the HDA controller runs the BDL cyclically, so a panic played the six-second cue and then wrapped to entry 0 and replayed into the cue's loud opening until the stop check noticed, which a delayed render tick made late enough to hear. `dnpr_audio_maybe_stop` now repoints every BDL entry the DMA has finished with at a page of silence as it goes, so a wrap should replay silence, and requests a stop at 5.9 s. Local PCM inspection found samples through 5.94 s, but peak amplitude falls to 1 after 5.9 s and zero by 5.95 s. This change is compiled into the installed #47 image but has not been verified by a panic recording after reboot. `dnpr_audio_start` rebuilds the cue's BDL, so a second start in one boot plays the cue again.

To build the experimental kernel source from this repository, run `make kernel-assets` with your own local game assets. This creates `kernel/dnpr_frame_blob.h`, `kernel/dnpr_live_blob.h`, and `kernel/dnpr_audio_blob.h`; all are excluded from Git because they contain game-derived data. Apply the patches to a matching Linux 6.15.2 tree, copy the DNPR C files, headers, and generated blobs from `kernel/` into `drivers/gpu/drm/`, enable `CONFIG_DRM_DNPR=y`, and build the kernel. DNPR must be linked into the kernel because the panic and CPU-stop hooks are built-in; `kernel/Makefile` only compiles the objects and intentionally does not build a `.ko`.

The Linux 6.15.2 DRM panic implementation requires the primary plane's `get_scanout_buffer` helper. Upstream NVIDIA 575.57.08 does not provide it. `kernel/nvidia-drm-panic.patch` adds that hook and block-linear writers for individual pixels and horizontal spans. DNPR batches adjacent changed scanout pixels into spans, which the NVIDIA writer copies in 16-pixel tile chunks instead of issuing one mapped write per pixel. Build #66 includes this optimization, but the user still reports about 30 fps. Build #67 fixes the status square: only bands shaded by helper CPUs count, bright yellow means strictly more than half, dark yellow means half or fewer, and red means timeout. The actual panic frame time still needs targeted measurement.

**Rebuild external GPU modules for the new kernel release** so normal desktop graphics can load. This alone only matches the kernel ABI; a panic display also needs a working scanout hook in the GPU module. This machine reuses `initramfs-linux.img`. It contains older kernel modules that cannot load into `6.15.2-dnpr`, but root storage and filesystem support are built into the kernel and matching NVIDIA modules live on the root filesystem. The machine has now booted `6.15.2-dnpr` with the reused initramfs and loaded the matching NVIDIA modules.
